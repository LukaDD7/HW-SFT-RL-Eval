# RLSD＋RLRT：环境、数据与启动准备

更新：2026-11-24。与主说明配套，目标是单节点 8×H200 的 CUDA 全参数 hybrid；不是阿里 PPU 环境，不是 OPSD-LoRA。

## 1. 先准备完整资产

建议目录（按自己的机器调整绝对路径）：

/workspace/hybrid/

  models/               Base、MOPD step351 的完整HF权重

本包提供核心参考代码、方法、直接依赖清单和准备工具。两个 HF 仓库包含题、图和结构化规则，但不提供原 OSS v3 Python 源码或原验证集；完整训练仓库也须另行交付。不能通过安装上游最新版 veRL 来替代我们修改过的 trainer/actor。`collect_original_run.py` 可在保留原启智共享目录的环境中只读归档旧代码和评分器。

## 2. 硬件与系统

- Linux x86_64，8 张 H200 同一节点，8 卡对训练进程可见；沿用原 CUDA/NCCL 网络和拓扑设置。
- Python 3.11；NVIDIA 驱动须支持 PyTorch 的 CUDA12.8 构建。`nvidia-smi` 中的 CUDA 字样是驱动能力，实际 torch runtime 由 `torch.version.cuda` 核对。
- 推荐沿用原镜像；重建时准备 C/C++ 编译器、`ninja`，从源码编译 FlashAttention 还需要匹配的 CUDA toolkit/nvcc。容器中开放 GPU 和足够共享内存，避免默认小容量 `/dev/shm`。
- 完整 checkpoint 包含 FP32 actor/Adam 状态和滞后教师，远大于 BF16 评测权重；400步、每50步且全保留可占约1TB量级，建议另留模型、数据、缓存和日志空间。具体以真实 checkpoint 大小计算，不是模型参数设置。

系统和可见性检查：

```bash
nvidia-smi
nvidia-smi topo -m
python3.11 --version
df -h /workspace /dev/shm
```

不要直接搬 PPU 的 torch、vLLM 插件或厂商定制 wheel 到 H200。

## 3. 环境版本及安装顺序

核心保持：torch2.8.0+cu128、torchvision0.23.0、torchaudio2.8.0、Transformers4.57.6、vLLM0.11.0、FlashAttention2.8.3、Ray2.53.0、OmegaConf2.3.1、qwen-vl-utils0.0.14。

直接依赖版本来自本地保留的旧 CUDA 环境记录。`environment/reference-pip-freeze.txt` 是取证快照，含当时的本地 wheel URL，不能原样拿去 pip install。`requirements-cuda.txt` 是重建直接依赖配方，**不是已在新 H200 主机验证过的全传递依赖锁**。若能取得原镜像/完整 wheelhouse，以实际已验证环境为先，不升级这些核心版本。

以下在接收方 Linux 训练机执行。命令中的 `PACKAGE` 与 `REPO` 必须指向真实路径：

```bash
python3.11 -m venv /workspace/hybrid/venv
source /workspace/hybrid/venv/bin/activate
export PACKAGE=/workspace/hybrid/handoff
export REPO=/workspace/hybrid/repo
python -m pip install --upgrade pip setuptools wheel packaging ninja

# 先固定CUDA torch，再安装依赖，防止装vLLM时换掉torch构建。
python -m pip install torch==2.8.0 torchvision==0.23.0 torchaudio==2.8.0 \
  --index-url https://download.pytorch.org/whl/cu128
python -m pip install -r "$PACKAGE/environment/requirements-cuda.txt"
```

FlashAttention 优先使用与 **cp311、Linux x86_64、CUDA12、torch2.8 和 CXX11 ABI** 对应的 2.8.3 wheel。旧环境记录的 wheel 文件名为 `flash_attn-2.8.3+cu12torch2.8cxx11abiTRUE-cp311-cp311-linux_x86_64.whl`，SHA256 为 `3d41b2fc55753faa7f45d6568ea73a96b96afb48b82994ab9b49bcbcb6c87588`；本包没有分发该二进制。仅有同版本号不保证 ABI 匹配。

```bash
python -c 'import torch; print(torch.__version__, torch.version.cuda, torch._C._GLIBCXX_USE_CXX11_ABI)'
# 已有匹配wheel时：
python -m pip install --no-deps /实际wheel路径/flash_attn-2.8.3+cu12torch2.8cxx11abiTRUE-cp311-cp311-linux_x86_64.whl
```

若没有 wheel，而主机已具备相匹配的 nvcc/toolkit，可改为源码安装（与上面的 wheel 安装二选一）：

```bash
nvcc --version
MAX_JOBS=8 python -m pip install flash-attn==2.8.3 --no-build-isolation --no-deps
```

最后安装原训练源码；`--no-deps` 避免 editable 安装把已锁核心版本再次升级。原 OSS v3 如有额外依赖，要根据其实际 imports 和原 freeze 补齐，不能凭评分器名字猜 `math_verify` 或32B服务。

```bash
cd "$REPO"
python -m pip install --no-deps -e .
python -m pip check
export CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7
python "$PACKAGE/check_environment.py" --out /workspace/hybrid/environment-check.json
python -m pip freeze > /workspace/hybrid/environment-installed.freeze.txt
```

环境检查会记录版本、ABI、可见GPU、每卡BF16小矩阵计算和 `pip check`。它不能替代实际模型加载、FSDP-vLLM权重同步、8卡collective、评分器及checkpoint恢复检查。检查文件已有则换新文件名，避免覆盖证据。发生 `undefined symbol` 优先检查 FlashAttention/torch ABI，不用盲目升级 Transformers/vLLM。

## 4. 下载与转换两套训练数据

固定版本：

```text
MOPD-route-v2-train-15k  6374961a4945f5ee7462520ecd54bcc93ee9d0bc
RL-RSTG-ZVP-train-15k  df005b52aead28acf57b05a1f30487a220d398bb
```

执行一次即可同时准备两条路线的数据。此命令下载约3.8GiB的两个发布Parquet集合（manifest字节数估算），另导出原图；不下载模型，不启动训练：

```bash
source /workspace/hybrid/venv/bin/activate
export HF_HOME=/workspace/hybrid/cache/huggingface
python /workspace/hybrid/handoff/prepare_hf_data.py \
  --out /workspace/hybrid/data
```

若事先离线下载了完整 snapshot，可用 `--snapshots /快照父目录`；其下应有 `mopd15k/`、`rstg15k/`，各含原 manifest 和20个Parquet分片。

输出：

| 文件 | 用途 |
|---|---|
| `base_mix30k.train.jsonl` | Base训练，两个仓库各15k完整拼接 |
| `mopd_rstg15k.train.jsonl` | MOPD训练，只含第二仓库15k |
| `images/` | 原始图片字节，内容哈希命名；`.img` 后缀由PIL按文件内容识别 |
| `data_manifest.json` | 数据版本、两份JSONL哈希、来源计数及精确内容指纹交集 |

转换器逐分片核验 manifest 的文件SHA256、字节数和行数，再核验每张原图 SHA256；遇损坏/格式不符直接报告，不吞掉样本。图片去重存储不会减少训练行。JSONL写绝对图片路径，移动到另一台机器时需按统一根重定位并重新记录JSONL哈希。

Base在转换文件中先放第一份15k、再放第二份15k；**不离线打乱**，由原 `data.shuffle=true, seed=1` 做一次确定的训练排列，避免无意增加第二层shuffle。每轮继续沿用原loader逻辑。来源比例是按行1∶1，不是每batch固定1∶1。

数据中的 `ground_truth` 是最终答案；不是teacher-CoT。`rule_solution_json` 及解析后的 `rule_solution` 完整保留，`teacher_id`等旧设置移入 `published_*` 来源字段。`problem_type`按答案类型映射到旧统一模板：选择题→multiple choice，数值→numerical，布尔→boolean，其余→open-ended；不改变题面或评分规则。选项已在题面中，不重复拼一遍 `Options:`；评分选项仍从结构化规则读取。

不要直接采用发布的 `prompt` 中 `<think>` system 指令：两条RL路线都保留旧 `unified.jinja` 的 `<thought>` 协议。不要用 `teacher_id` 选择外部教师；本实验教师就是同初始化滞后副本。

### 独立验证集

两个 HF 仓库只有 train。为保留全量30k/15k，不默认从中划走验证题；继续使用原实验独立val，验证频率50及其余设置不变。原 val 未交付时属于尚未补齐的运行资产，不能以train兼作val，也不能声称完整复现。合并后需再检查val与两份train的来源ID及内容交集；发生交集要单独说明和解决，不能悄悄丢训练行。

## 5. 模型初始化与教师

Base用 `Qwen/Qwen3-VL-8B-Instruct`，不能替换成Thinking或Stage1模型；MOPD用 `lzy-vlm-lab-opd/qwen3-vl-8b-iso-mopd-route-v2-step351` 的固定revision `f9582f3594ba0a47e513a50b658204e7c322fbbb`。包含processor/tokenizer/chat_template/config等完整HF文件。

Base旧run的下载revision未取回。新运行必须记录自己实际下载的commit，不要把下面查询到的当前commit说成历史commit：

```bash
python - <<'PY'
import json
from pathlib import Path
from huggingface_hub import HfApi, snapshot_download
root = Path('/workspace/hybrid/models')
root.mkdir(parents=True, exist_ok=True)
base_repo = 'Qwen/Qwen3-VL-8B-Instruct'
base_rev = HfApi().model_info(base_repo).sha
mopd_repo = 'lzy-vlm-lab-opd/qwen3-vl-8b-iso-mopd-route-v2-step351'
mopd_rev = 'f9582f3594ba0a47e513a50b658204e7c322fbbb'
for repo, rev, folder in [(base_repo, base_rev, 'Qwen3-VL-8B-Instruct'),
                          (mopd_repo, mopd_rev, 'MOPD-route-v2-step351')]:
    snapshot_download(repo, revision=rev, local_dir=str(root/folder), max_workers=8)
record = {'base': {'repo': base_repo, 'revision': base_rev},
          'mopd': {'repo': mopd_repo, 'revision': mopd_rev}}
(root/'download_revisions.json').write_text(json.dumps(record, indent=2), encoding='utf-8')
PY
```

每条路线的学生与独立教师从**同一**起点初始化；新RL从step0计步。没有从HF的 `teacher_id` 指向外部教师；没有LoRA。教师前向额外输入最终答案，按原学生token轨迹评分，每10步在更新后硬同步，λ在200步衰减为0。

## 6. 原 OSS v3 的接线与最小验收

数据卡写OSS v5不改变本次旧v3评分器选择。保留原 `reward_function`、函数名、kwargs、依赖源码及SHA256。v3如何消费规则metadata必须看原源码，而非猜测。

每条路径都要检查：Parquet规则 → JSONL原规则/parsed规则 → collate非张量metadata → reward manager输入 → 原OSS v3 → accuracy/judgeable → UID整组掩码。若原v3要求不同字段结构，只作无损接口映射，不能改其判分逻辑；不可把最终答案替换成整段rule JSON给teacher。

至少回放两份数据中的选择、数值、布尔、文本/多答案等实际存在类型：给定正确最终答案应按原v3判对，明确错误应判错，不可靠匹配则沿原逻辑unknown。用实际原评分器测试，而非另写一个“看起来一样”的评分器。保存按dataset/answer_type的数量、judgeable比例和verdict；检查rule options/references/tolerance未丢失。

八条全可判分且1～7对才是非零优势混合组；全对/全错优势为0；任何unknown整组屏蔽。筛选或数据发布时的可判分性不保证新rollout一直可判，不能把高mask率理解成实现必然正确。若新数据类型不被旧v3支持，应明示数据兼容性问题，不能偷偷换v5。

## 7. 完整配置、启动与记录

先取得原hybrid完整runtime配置，按主说明10.2节分别生成Base与MOPD两份；本包 `configs/experiment_recipe.json` 是数据与参数合同，**不是能直接交给训练入口的完整配置**。旧 `HISTORICAL_BASE_CONFIG_NOT_MOPD.yaml` 只作取证，仍带旧数据/评分器路径，也不能直接当新配置运行。

保持400步、teacher decay200、batch256×8、lr1e-6、seed1、每50步完整保存。Base扩大题库后曝光次数减少，但不改总步数或其他参数。参考CPU检查可以在训练环境运行：

```bash
cd /workspace/hybrid/handoff/reference_code
python -m unittest discover -s tests -p 'test_*.py'
```

新原生8卡进程启动前核对：实际imports来自原仓库；old/current/teacher token对齐；同8卡交替rollout/update；固定模板只应用一次；生成后vLLM释放/休眠；short Ray temp目录；没有错误残留 `load_checkpoint_path`。CPU helper测试不覆盖完整reward路径或GPU训练。

交互式实例后台启动（先把真实配置放到指定路径，两条路线各用独立run名，一次只运行一个）：

```bash
source /workspace/hybrid/venv/bin/activate
cd /workspace/hybrid/repo
export PYTHONPATH="$PWD${PYTHONPATH:+:$PYTHONPATH}"
export CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7
export RAY_TMPDIR=/tmp/hybrid-ray
export TMPDIR=/tmp/hybrid-tmp
export PYTHONUNBUFFERED=1
mkdir -p "$RAY_TMPDIR" "$TMPDIR" /workspace/hybrid/logs
RUN=base-mix30k-hybrid-h200
CONFIG=/workspace/hybrid/configs/base-mix30k-hybrid-h200.yaml
PYTHON=/workspace/hybrid/venv/bin/python
test -s "$CONFIG" || exit 1
nohup "$PYTHON" -u -m verl.trainer.opsd_main "config=$CONFIG" \
  >"/workspace/hybrid/logs/$RUN.log" 2>&1 </dev/null &
echo "PID=$!"
echo "LOG=/workspace/hybrid/logs/$RUN.log"
```

MOPD版只换成对应的MOPD完整配置及run名。若原launcher会做manifest、锁和路径检查，优先使用其前台入口，外层用nohup；本节底层模块不保证自动补齐原launcher的审计输出。平台分布式任务应以前台命令保持主进程存活，不能nohup后直接让作业入口退出。

首步记录256题/2048条、两数据源计数、mixed/all-correct/all-wrong/unknown组数、非零优势token、实际λ（第1步0.4975）、教师权重clip比例、loss/grad norm、截断率和耗时。后续核对step10教师更新顺序、step50完整checkpoint、step200关闭教师。导出HF学生用于评测，真正续训仍需actor/optimizer/teacher/RNG/dataloader完整状态。B15评测seed43不应写入训练seed配置。
